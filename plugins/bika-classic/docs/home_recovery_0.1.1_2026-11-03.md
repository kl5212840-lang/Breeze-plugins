# 0.1.1 本地候选：首页分区失败恢复

本轮只修改 `plugins/bika-classic`。原 Bika、JM、八份交付 CJS、商城索引与宿主不在本轮修改范围。保持首页、分类、视频、我的四项结构，独立 UUID、账号和本机记录边界保持。

## 选择这个缺口的依据

0.1.0 首页用 `Promise.all` 等待更新与榜单，一个请求失败会让整页失败，另一个成功分区也无法显示。真实 CJS fixture 已复现冷启动单区失败和已有内容刷新失败，两项在修复前失败，见本目录上一级 `dist/validation/home-recovery-before.log`。

故障由离线合成适配注入，只证明异常隔离的代码问题，不说明真实站点、代理或用户当时网络的失败原因；没有为诊断网络修改代理或绕过健康缓存。

已核对宿主：`PluginFunctionContent` 在加载时替换为 spinner；当前协议没有原地刷新或下拉刷新动作。不能只在插件文案里发明“下拉重试”，也不能递归打开一层首页充当刷新。本轮沿用分区标题的真实完整列表动作，让失败分区进入现有可重试列表，返回仍由原导航栈处理。

## 实施的行为

- 更新、24 小时热门独立处理结果。单区失败保留另一区；同一账号、认证代际、API 地址、分流和屏蔽条件内，失败区可继续显示上次成功内容，并明确显示“更新失败”。从未成功的分区显示“加载失败”，不会伪装成成功的空结果。
- 失败分区标题提供“列表重试”：更新进入既有搜索结果列表；热门进入真实 `getRankingData` 场景，保留 `bikaRanking` 布局声明。未新增占位按钮或递归首页路由。
- 使用与成熟适配相同、已经核实的 `comics/advanced-search?page=1`（`sort: dd`、空关键词/分类）及 `comics/leaderboard?tt=H24&ct=VC`；最新列表保持原先不缓存，榜单保持 `client.ts` 已有的 10 分钟健康请求缓存，不增加 TTL、不清空或禁用健康缓存。榜单继续使用原哈希键合同（origin/channel/method/path/body/authorization/quality），本预览固定捕获的 authorization 参与键，避免跨账号借用。没有新增 API、域名、官方素材或真实账号请求。
- 正常空数据清除旧预览；无效响应和逻辑拒绝保留旧内容并标记失败。未授权仍抛出当前独立源的登录合同，不拿旧内容冒充登录成功。
- 每个分区最多扫描返回的前 100 行、显示 12 项；先应用已有分类屏蔽，再映射预览。只保留当前条件的两份预览，最多 24 项，位于 runtime 内存，不写数据库、磁盘或云端。返回数据与内部快照分离。
- 相同条件的并发首页读取合并为最多两条网络请求；有健康榜单缓存时不重复请求。账号、线路、分流或屏蔽条件变化后不沿用旧预览，晚回复不能重新填入新快照。退出只丢弃本插件内存预览，不清空其他请求缓存。不增加自动重试或后台轮询。
- 明确认证失败及时返回当前源登录合同，不等待另一条慢请求；所有已发分区任务的结果仍由 `allSettled` 接住，不取消全源请求，也不忽略仍在途的拒绝。

## 验证与未完成项

32 项真实 CJS 离线 fixture 通过，覆盖单区/双区失败、保留与恢复、完整列表动作实际调用、正常空数据/无效响应、并发、授权和访问条件变化、晚回复、未授权不回填、返回数据不可修改内部快照、退出清理、健康缓存命中和单键失效。需要模拟过期时只把 fixture 自己的缓存标为过期，不调整生产策略。全部是合成网络和存储，不加载用户资料或打开 socket。

本轮可以证明请求结束后的分区返回合同，不能证明等待期间正文连续。宿主仍可能在 load 期间显示整页 spinner，且从子列表返回不会自动刷新旧首页的失败提示；这些需要后续宿主状态接入，未在本轮更改。系统/Breeze 样式、浅深主题、小屏大字及真实转场尚未做 SDK/设备验证，不宣称视觉验收通过。

## 明确无效业务响应的局部缓存处理

现有共享 `client` 按 HTTP 成功存放响应，合成 `{code:500}` 等无效业务响应也可能留下。当前真实 CJS 的 RED 已复现它在下一次显式尝试阻挡健康结果，记录为 `dist/validation/home-invalid-cache-before.log`。这不说明真实站点发生过这种响应，也不判断用户当前代理故障原因；共享 client 同类范围已留给主任务下一批评估，冻结的八份 CJS 不改。

仅本首页的 `home-request.ts` 用已有 `client` / `buildCacheKey` / `readCache` 构成薄适配，一次捕获 channel，缓存查找、`__bikaChannel`、`__cacheKey` 使用同一捕获值。确认为无效的榜单业务响应，只对当次实际请求键重新读取并验证仍无效的 entry，调用现有 `cache.compareAndSet(key, entry, null)` 原子失效。`readCache` 把 null 视为 miss；不扫描缓存、不猜 hash、不全量删除，不补发自动请求。下一次用户明确调用时才按原缓存未命中流程请求。

健康并发写入会使 CAS 失败，从而保留健康结果。fixture 已证明账号、channel 和 API origin 其他键不被动到，切回条件可继续命中原健康缓存；健康榜单仍保持 10 分钟 TTL。已核对 Axios fetch 只把明确的 HTTP 字段送入 `Request`，实际成品 fixture 也检查内部 `__` 元数据没有进入 URL、headers 或 body。缓存维护不可用时仍返回原分区/认证失败，不冒称修复成功。

最终日志：`dist/validation/home-recovery-0.1.1-final.log`。认证尽早返回的 RED 为同目录 `home-auth-failfast-before.log`；请求级证明不替代真实宿主/设备验收。

仍待固定可核对的官方版本基准，社区、消息、官方专属推荐及动画没有新增实现。此版本是独立社区适配的质量候选，不代表完整官方 App。

一次性导入仍由宿主实现，保留 `recordImport: unavailable`，不加导入按钮。建议宿主完成后只消费明确的来源/目标 UUID、媒体类型、真实站点 ID/视频命名空间及能力版本；复用现有 `getReadSnapshot`/视频详情合同核对可识别性，账号、令牌、Cookie、临时播放地址不进入记录导入声明。没有新增 `legacySources` 或自动搬运资料。
